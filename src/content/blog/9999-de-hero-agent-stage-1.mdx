## Motivation

In the <FancyLink linkText="Building a Data Engineering Hero Agent" url="https://villoro.com/blog/data-engineering-hero-agent-vision/" dark="true"/> post I described the vision: a centralized service that takes over the manual on-call "hero" work, designed to gain autonomy in stages. This post is about **Stage 1 — Report**: the part that's actually running.

Stage 1 has no AI yet, and that's on purpose. Before a model summarizes anything, the plumbing around it has to be solid: structured ingestion, deduplication, clean alerts, and a service that never drops a failure even when parts of it are broken.

> [!note]
> The AI (via AWS Bedrock) comes in a later stage. Stage 1 is all the engineering around the spot where the model will eventually plug in.

## Why a synchronous FastAPI service

It's a small <FancyLink linkText="FastAPI" url="https://fastapi.tiangolo.com/" company="fastapi"/> service. Jobs stop posting their own Slack alerts and instead `POST /failures` with a structured event. The service then decides whether to alert, posts to Slack, and stores the event.

FastAPI is the obvious choice for a small Python service like this, and it gives me Pydantic validation and a free OpenAPI schema on top. The decision I actually thought about was making it synchronous.

The handlers are plain `def`, not `async def`. Each request does one blocking Postgres write (through `psycopg`'s sync driver) and one blocking HTTP call to Slack. There's no concurrent I/O to overlap, so `async` would only add noise. FastAPI runs sync handlers in a thread pool, and that's more than enough here: the service only sees traffic when a job fails, so it will never be under real load.

> [!note]
> I considered putting a queue (SQS or an EventBridge bus) in front of ingestion, so a slow Slack call or a database hiccup couldn't block a producer. I skipped it. A queue mainly buys durability, and the fail-safe design further down already provides that: accept and log, alert before persist, never raise. A queue would be a second mechanism for the same problem and one more thing to operate, for a service whose whole input is the occasional failed job.

The whole thing is small, a handful of modules that each do one job:

| Module         | Responsibility                                          |
| -------------- | ------------------------------------------------------- |
| `schemas.py`   | The `FailureEvent` payload jobs send (Pydantic).        |
| `decisions.py` | *Should* this event alert? (deterministic dedup policy) |
| `alerts.py`    | Build the Slack message.                                |
| `slack.py`     | Post it.                                                 |
| `models.py` / `db.py` | The SQLAlchemy model and engine/session setup.   |
| `main.py`      | Wire it together, and never crash the alerting path.    |

## The structured event

The core idea is that jobs send structured data instead of a pre-formatted Slack string. This is the payload:

<FileName>
  de_hero/schemas.py
</FileName>
```python
class FailureEvent(BaseModel):
    model_config = ConfigDict(extra="forbid")

    app: SourceApp = Field(description="System the job ran in.")
    job_name: str = Field(min_length=1)
    owner: str | None = Field(default=None, min_length=1)

    prefect_flow_id: str | None = None
    parent_flow_run_id: str | None = None
    failed_items: list[FailedItem] = Field(default_factory=list)

    exception_type: str | None = None
    error_message: str | None = None
    traceback: str | None = None
    exit_code: int | None = None

    occurred_at: datetime = Field(default_factory=_now_utc)
    metadata: dict[str, str] = Field(default_factory=dict)
```

A few decisions worth calling out:

- **`extra="forbid"`** means an unexpected field returns a `422` instead of being silently swallowed. If a producer sends the wrong shape, I want to hear about it.
- **`owner`** is what lets an alert ping the right person automatically. It's optional because not every producer tracks ownership, and those alerts simply carry no mention.
- There are two ways to report a failure: a **top-level** one for a single ECS task, and a list of **`failed_items`** for a run that ends with several failures at once. (A flow-level alert usually fires once, at the end of a run.) `FailedItem` is intentionally generic: an id, an optional status, an optional owner, and the same exception/message/traceback fields. That way a failure that isn't a single Python exception still fits, without needing a producer-specific schema.

## The tricky part: who sends the alert?

This is the part that makes the service more than a webhook. To see why, it helps to know how the jobs run. The orchestrator, <FancyLink linkText="Prefect" url="https://www.prefect.io/" dark="true"/>, decides what runs and when, but it doesn't run the heavy work itself. It triggers each job as a separate task on ECS, in its own container. So the code that can notice a failure lives in two places: the orchestrator, which sees that a task failed, and the task itself, which has the actual exception, traceback, and exit code.

Both of them report to the service, so a single failure can arrive twice:

- The **ECS task** reports its own failure. It has the richest context, so its alert is the one we want.
- The **Prefect flow** that triggered the task also notices it failed, and reports too.

If both report, the hero gets two Slack messages for one problem. But if I just silence the Prefect side, I lose the alert completely when the ECS task dies before it can report anything (an OOM kill, for example). In that case the orchestrator is the only one that knows something went wrong.

The rule that resolves this lives in its own module. These decisions are deterministic and owned by the application, never by the model:

<FileName>
  de_hero/decisions.py
</FileName>
```python
def should_notify(event: FailureEvent, session_factory) -> bool:
    # ECS always alerts — it has the richest context.
    if event.app is SourceApp.ecs:
        return True

    # No DB or nothing to correlate on → alert rather than risk dropping.
    if session_factory is None or not event.prefect_flow_id:
        return True

    # A Prefect flow alerts only if its ECS task hasn't already.
    try:
        return not _ecs_already_notified(session_factory, event.prefect_flow_id)
    except SQLAlchemyError as error:
        logger.error("alert-dedup lookup failed, notifying anyway: {}", error)
        return True
```

The correlation works like this: the Prefect flow passes its own `prefect_flow_id` down to the ECS task it triggers, and the task echoes it back as `parent_flow_run_id`. So checking "did the ECS task already alert for this run?" is a lookup for a notified event whose `parent_flow_run_id` matches the Prefect flow's id.

> [!tip]
> Every branch is biased the same way: when in doubt, alert. No database, no flow id, or a failed query all fall through to notifying. A duplicate alert is annoying, but a dropped failure is a production incident.

## Building the Slack alert

This is what the Report stage is for: turning a structured event into one clean message instead of a raw stack trace dumped into a channel.

### Building the message

Building the message is a pure function, so the same event always produces the same Slack blocks. That keeps it easy to test, and later it lets the AI summary replace a single block instead of rewriting the whole thing:

<FileName>
  de_hero/alerts.py
</FileName>
```python
def build_alert_payload(failure_id: UUID, event: FailureEvent) -> dict[str, Any]:
    """Build a Slack webhook payload for a failure event. Pure and deterministic."""
    mention = f"{resolve_mention(event.owner)} " if event.owner else ""
    header = f"{mention}:x: *{_job_label(failure_id, event)} failed*"

    blocks = [{"type": "section", "text": {"type": "mrkdwn", "text": header}}]
    if event.failed_items:
        blocks += _render_failed_items(event)  # one summary per distinct error
    else:
        blocks += _render_single_failure(event)  # exception + cropped traceback

    return {
        "attachments": [
            {
                "color": _level_color(event),
                "fallback": f"{event.job_name} failed",
                "blocks": blocks,
            }
        ],
    }
```

A few small things do most of the work here:

- The **`owner` becomes a real `@`-mention** in the header, so the right person is pinged before anyone has to triage. This is probably the most useful line in the alert.
- The **job name links to the failure's de-hero detail page** rather than the raw Prefect run, so following up is one click and there's a place to add richer context later.
- The **traceback is cropped to its last few lines**, which is where the real error almost always is; the rest is usually import machinery. A `metadata["slack_level"]` value picks the colored bar (`error`/`warning`/`info`) so severity is visible at a glance.

### Posting it

Posting it is a plain webhook `POST`. Because it sits on the alerting path, it's written to never raise:

<FileName>
  de_hero/slack.py
</FileName>
```python
def post_alert(webhook_url: str, payload: dict[str, Any]) -> bool:
    """Post to a Slack incoming webhook. Returns True on success. Never raises."""
    try:
        response = httpx.post(webhook_url, json=payload, timeout=5.0)
        response.raise_for_status()
        return True
    except httpx.HTTPError as error:
        logger.error("failed to post Slack alert: {}", error)
        return False
```

That `bool` return matters: it's the "did Slack actually accept the post?" signal the dedup and fail-safe logic rely on. A Slack outage turns into a `False`, not an exception that fails the whole ingestion request.

The result is the change the vision post promised. Instead of a 60-line traceback, the hero gets:

```txt
@data-platform ❌ salesforce_extract failed
ConnectionError: HTTPSConnectionPool: Max retries exceeded (429 Too Many Requests)
  File "extract/salesforce.py", line 88, in fetch_page
    resp.raise_for_status()
```

It's the same failure, but now it names the owner, links to the detail page, and leads with the line that matters.

## Fail-safe on the alerting path

This is the rule that shapes `main.py`. The service sits in the production alerting path, so if it's down, the database is unreachable, or Slack times out, the failure still has to surface. The guiding principle is to degrade, never swallow.

That shows up in three places:

- **No database?** Accept and log the event anyway, skip storing it.
- **Storage fails?** Still send the alert, and also post an internal alert so the hero knows the audit trail is missing a row.
- **Slack post fails?** Record the event as *not notified*, so a later Prefect-side event can still be the fallback.

Here's the ingestion handler, trimmed to the essentials. `_alert` is just the `build_alert_payload` and `post_alert` pair from the section above, and returns whether the post went out:

<FileName>
  de_hero/main.py
</FileName>
```python
@app.post("/failures", status_code=202, dependencies=[Depends(require_ingest_token)])
def submit_failure(event: FailureEvent) -> FailureAccepted:
    failure_id = uuid7()  # time-sortable id

    notify = should_notify(event, app.state.session_factory)

    # Alert BEFORE persisting, and record whether Slack actually accepted it.
    delivered = False
    if notify:
        delivered = _alert(failure_id, event, app.state.slack_webhook_url, ...)

    persisted = _persist(failure_id, event, delivered, app.state.session_factory)

    # A configured DB that fails to store → the audit trail is silently
    # losing rows. Surface that in Slack, not just the logs.
    if not persisted and app.state.session_factory is not None:
        _alert_internal_error(failure_id, event, ...)

    return FailureAccepted(id=failure_id, job_name=event.job_name)
```

Two details hide in that order of operations:

- We **alert before we persist**. If the process crashes between the two we might alert twice, and that's the failure mode I want. Duplicates beat dropped alerts.
- The stored `notified` flag records whether Slack actually accepted the post, not just whether we decided to send it. A later Prefect-side event reads that flag to decide whether to stay quiet, so a failed post must never suppress the fallback.

`_persist` itself is also written to never raise:

<FileName>
  de_hero/main.py
</FileName>
```python
def _persist(failure_id, event, notified, session_factory) -> bool:
    """Store an event; return True if actually stored. Never raises."""
    if session_factory is None:
        logger.warning("no database configured; not persisted (id={})", failure_id)
        return False

    record = FailureEventRecord(
        id=failure_id,
        occurred_at=event.occurred_at,
        prefect_flow_id=event.prefect_flow_id,
        parent_flow_run_id=event.parent_flow_run_id,
        notified=notified,
        payload=event.model_dump(mode="json"),
    )
    try:
        with session_factory() as session:
            session.add(record)
            session.commit()
    except SQLAlchemyError as error:
        logger.error("failed to persist (id={}): {}", failure_id, error)
        return False
    return True
```

> [!warning]
> A database outage must not turn a failure report into a `500` and a lost alert. Every path that touches storage or Slack either degrades gracefully or is caught. The only deliberate exception is a bad ingest token, which returns `401`.

## Why a shared bearer token, not something fancier

`/failures` sits behind a single shared token, checked with a plain `Authorization: Bearer` header. I could have used per-producer credentials, mTLS, or SigV4-signed requests, but the threat model is narrow. Every caller is a job I control, running in my own AWS account, and the token only needs to keep someone else's traffic off the ingestion path. A shared secret checked on every request does that, and it's trivial for a Prefect flow or an ECS task to send. If de-hero ever accepts events from outside my own infrastructure this is the first thing I'd change, but not before.

## Talking to Postgres

Storage is plain <FancyLink linkText="SQLAlchemy" url="https://www.sqlalchemy.org/" dark="true" company="default"/> against RDS Postgres, with a sync driver and no ORM tricks, matching the rest of the service.

### Engine and sessions

<FileName>
  de_hero/db.py
</FileName>
```python
def build_engine(database_url: str) -> Engine:
    return create_engine(database_url, pool_pre_ping=True)


def build_session_factory(engine: Engine) -> sessionmaker[Session]:
    return sessionmaker(bind=engine, expire_on_commit=False)
```

At startup `main.py` builds a single engine and session factory, and stores the factory on `app.state`. Each request then opens its own short-lived session (`with session_factory() as session: ...`) instead of sharing one connection.

The one flag worth calling out is `pool_pre_ping`. RDS silently drops idle connections, and without it the first request after a quiet spell fails with a confusing "connection already closed" error. With it, SQLAlchemy checks the connection before handing it over and reconnects if needed.

### The failure_events table

There's a single table, `failure_events`. Each event is one row: the validated payload stored as JSON, plus a few columns pulled out for the things I actually query on:

<FileName>
  de_hero/models.py
</FileName>
```python
class FailureEventRecord(Base):
    __tablename__ = "failure_events"

    id: Mapped[UUID] = mapped_column(Uuid, primary_key=True)  # UUIDv7
    occurred_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), index=True)
    received_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), onupdate=func.now()
    )
    job_name: Mapped[str] = mapped_column(String, index=True)
    app: Mapped[str] = mapped_column(String, index=True)
    parent_flow_run_id: Mapped[str | None] = mapped_column(
        String, nullable=True, index=True
    )
    notified: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    payload: Mapped[dict[str, Any]] = mapped_column(JSON)
```

The `id` is a **UUIDv7**, which is time-sortable, so ordering by id also orders rows chronologically and I don't need a separate index for that.

Every other column follows one rule: a field stays inside `payload` until I actually need to query or filter on it, and only then does it get promoted to its own indexed column. So far that means:

- `job_name` and `app` back the frontend's filters
- `parent_flow_run_id` backs the dedup lookup
- `notified` is read by a later Prefect-side event

Nothing is pulled out before there's a query that needs it.

`updated_at` is the one exception, there by convention rather than because this service queries it. Every table in our warehouse carries an `id` and an `updated_at` that bumps itself on any change (`onupdate=func.now()`, so I never set it by hand). Our datalake extraction relies on that: it pulls new and changed rows incrementally by asking each table for everything updated since its last run. Following the convention means `failure_events` lands in the datalake like any other table, with no special handling.

## Migrating the schema with Alembic

Because columns get promoted only when they're needed, the schema changes often and in small steps as features land, rather than all at once up front. That's what <FancyLink linkText="Alembic" url="https://alembic.sqlalchemy.org/" dark="true" company="default"/> is for. Each change is a single migration file with an `upgrade`/`downgrade` pair, chained to the previous one by a revision id, so it's easy to review and to revert. Here's a real migration from the project, pulling `job_name` out of the JSON payload once the frontend needed to filter on it:

<FileName>
  migrations/versions/..._add_job_name.py
</FileName>
```python
def upgrade() -> None:
    op.add_column(
        "failure_events",
        sa.Column("job_name", sa.String(), nullable=True),
    )
    op.execute("UPDATE failure_events SET job_name = payload->>'job_name'")
    op.alter_column("failure_events", "job_name", nullable=False)
    op.create_index(op.f("ix_failure_events_job_name"), "failure_events", ["job_name"])


def downgrade() -> None:
    op.drop_index(op.f("ix_failure_events_job_name"), "failure_events")
    op.drop_column("failure_events", "job_name")
```

The shape is always the same: add the column as nullable, backfill it from data that already exists (here, straight from the JSON payload with Postgres's `->>` operator), then tighten it to `NOT NULL`. Splitting it into three steps means existing rows don't break the migration, which a single "add a `NOT NULL` column" step would risk.

> [!tip]
> Alembic can autogenerate a migration by diffing the ORM models against the live schema (`alembic revision --autogenerate`), but for anything with a backfill step like this one the generated file is only a starting point. The model change is mechanical; the data migration isn't.

This is the start of the audit trail from the vision post. For now it only records what failed. Once Stage 2 adds human actions on top, this same store becomes the evidence for deciding what's safe to automate.

## Where this leaves us

Stage 1 is deliberately boring where it counts: no AI, no queue, no fancy auth. Just structured events, correct deduplication, clean Slack alerts, and a firm guarantee that failures reach a human. Every choice here favors that guarantee over performance or generality, and it's the foundation the rest of the project sits on.
