## Motivation

In the <FancyLink linkText="Building a Data Engineering Hero Agent" url="https://villoro.com/blog/data-engineering-hero-agent-vision/" dark="true"/> post I described the vision: a centralized service that takes over the manual on-call "hero" work, designed to gain autonomy in stages. This post is about **Stage 1 — Report**: the part that's actually running.

Stage 1 has no AI yet, and that's on purpose. Before a model summarizes anything, the plumbing around it has to be solid: structured ingestion, sane deduplication, clean alerts, and — most importantly — a service that **never drops a failure**, even when parts of it are broken.

> [!note]
> The AI (via AWS Bedrock) is a *later* stage. The interesting engineering in Stage 1 is everything around where the model will eventually plug in.

## Why a synchronous FastAPI service

It's a small <FancyLink linkText="FastAPI" url="https://fastapi.tiangolo.com/" company="fastapi"/> service. Jobs stop posting their own Slack alerts and instead `POST /failures` with a structured event. The service decides whether to alert, posts to Slack, and stores the event.

FastAPI earns its place for one reason mostly: the `FailureEvent` schema (below) *is* the API contract, and Pydantic gives me validation, a `422` on a malformed payload, and (eventually) an OpenAPI schema producers can generate a client from, all from the same class. That's worth more here than raw throughput, since this service handles failed job runs, not user traffic — it's never going to see meaningful load.

That's also why the handlers are plain `def`, not `async def`. Every request does one blocking Postgres write (via `psycopg`'s sync driver) and one blocking HTTP call to Slack — there's no concurrent I/O to overlap, so `async` would add ceremony without buying anything. FastAPI happily runs sync handlers in a thread pool, which is all the concurrency this workload needs.

> [!note]
> I also considered putting a queue (SQS, or an EventBridge bus) in front of ingestion, so a slow Slack call or a DB hiccup couldn't block a producer. I skipped it: a queue buys you durability, and durability is exactly what the fail-safe design further down provides directly — accept-and-log, alert-before-persist, never raise. Adding a queue on top would be two mechanisms solving the same problem, plus another moving part to operate, for a service whose entire input is "a job occasionally fails."

The whole thing is deliberately tiny — a handful of modules, each with one job:

| Module         | Responsibility                                          |
| -------------- | ------------------------------------------------------- |
| `schemas.py`   | The `FailureEvent` payload jobs send (Pydantic).        |
| `decisions.py` | *Should* this event alert? (deterministic dedup policy) |
| `alerts.py`    | Build the Slack message.                                |
| `slack.py`     | Post it.                                                 |
| `models.py` / `db.py` | The SQLAlchemy model and engine/session setup.   |
| `main.py`      | Wire it together, and never crash the alerting path.    |

## The structured event

The core of the whole design is that jobs send **structured data**, not a pre-formatted Slack string. This is the payload:

<FileName>
  de_hero/schemas.py
</FileName>
```python
class FailureEvent(BaseModel):
    model_config = ConfigDict(extra="forbid")

    app: SourceApp = Field(description="System the job ran in.")
    job_name: str = Field(min_length=1)
    owner: str | None = Field(default=None, min_length=1)

    prefect_flow_id: str | None = None
    parent_flow_run_id: str | None = None
    failed_items: list[FailedItem] = Field(default_factory=list)

    exception_type: str | None = None
    error_message: str | None = None
    traceback: str | None = None
    exit_code: int | None = None

    occurred_at: datetime = Field(default_factory=_now_utc)
    metadata: dict[str, str] = Field(default_factory=dict)
```

A couple of decisions worth calling out:

- **`extra="forbid"`** — an unexpected field is a `422`, not a silently swallowed typo. If a producer sends the wrong shape, we want to know.
- **`owner`** exists so the single most useful thing an alert can do — ping the *right* person — is automatic. It's optional because not every producer tracks one; those alerts just carry no mention.
- Both a **top-level failure** (a single ECS task) and a list of **`failed_items`**  are supported, because a flow-level alert usually fires once at the end of a run and may carry several failures. `FailedItem` is deliberately generic (an id, an optional status, an optional owner, plus the same exception/message/traceback shape) rather than "a Prefect task": a run can fail in ways that aren't a single Python exception, and this one field covers those too without a producer-specific schema.

## The tricky part: who sends the alert?

Here's the problem that makes this more than a glorified webhook. A single logical failure can be reported **twice**:

1. A Prefect **worker flow** triggers an **ECS child** task.
2. The ECS task fails and reports its own failure.
3. The worker flow sees the child failed and *also* reports.

If both alert, the hero gets two Slack messages for one problem. If we naively silence the worker, we lose the alert entirely when the ECS task dies *before* it can report (say, an OOM kill).

The rule that resolves this lives in its own module, because these decisions are **deterministic and application-owned** — never the model's:

<FileName>
  de_hero/decisions.py
</FileName>
```python
def should_notify(event: FailureEvent, session_factory) -> bool:
    # ECS always alerts — it has the richest context.
    if event.app is SourceApp.ecs:
        return True

    # No DB or nothing to correlate on → alert rather than risk dropping.
    if session_factory is None or not event.prefect_flow_id:
        return True

    # A Prefect worker alerts only if its ECS child hasn't already.
    try:
        return not _ecs_already_notified(session_factory, event.prefect_flow_id)
    except SQLAlchemyError as error:
        logger.error("alert-dedup lookup failed, notifying anyway: {}", error)
        return True
```

The correlation trick: the worker passes its own `prefect_flow_id` down to the child, and the child echoes it back as `parent_flow_run_id`. So "did ECS already alert for this run?" is just a lookup for a **notified** event whose `parent_flow_run_id` matches this worker's flow id.

> [!tip]
> Notice the bias in every branch: **when unsure, alert.** No database, no flow id, a failed query — all fall through to notifying. A duplicate alert is annoying; a dropped failure is a production incident.

## Fail-safe on the alerting path

This is the rule that shapes `main.py`. The service sits **in the production alerting path**. If it's down, the database is unreachable, or Slack times out — the failure still has to surface. So the guiding principle is **degrade, never swallow**.

That shows up in three places:

- **No database?** Accept and log the event anyway, skip storing it.
- **Storage fails?** Still send the alert — and post an *internal* alert so the hero knows the audit trail is missing a row.
- **Slack post fails?** Record the event as *not notified*, so a later worker event can still be the fallback.

Here's the ingestion handler, trimmed to the essentials:

<FileName>
  de_hero/main.py
</FileName>
```python
@app.post("/failures", status_code=202, dependencies=[Depends(require_ingest_token)])
def submit_failure(event: FailureEvent) -> FailureAccepted:
    failure_id = uuid7()  # time-sortable id

    notify = should_notify(event, app.state.session_factory)

    # Alert BEFORE persisting, and record whether Slack actually accepted it.
    delivered = False
    if notify:
        delivered = _alert(failure_id, event, app.state.slack_webhook_url, ...)

    persisted = _persist(failure_id, event, delivered, app.state.session_factory)

    # A configured DB that fails to store → the audit trail is silently
    # losing rows. Surface that in Slack, not just the logs.
    if not persisted and app.state.session_factory is not None:
        _alert_internal_error(failure_id, event, ...)

    return FailureAccepted(id=failure_id, job_name=event.job_name)
```

Two subtle points hide in that order of operations:

- We **alert before we persist**. If the process crashed between the two, we could double-alert — and that's the *correct* failure mode. Duplicates over dropped alerts.
- The stored `notified` flag records whether Slack **actually accepted** the post, not just whether we *decided* to send it. A later worker event reads that flag to decide whether to stay quiet — so a failed post must never suppress the fallback.

And `_persist` itself is written to never raise:

<FileName>
  de_hero/main.py
</FileName>
```python
def _persist(failure_id, event, notified, session_factory) -> bool:
    """Store an event; return True if actually stored. Never raises."""
    if session_factory is None:
        logger.warning("no database configured; not persisted (id={})", failure_id)
        return False

    record = FailureEventRecord(
        id=failure_id,
        occurred_at=event.occurred_at,
        prefect_flow_id=event.prefect_flow_id,
        parent_flow_run_id=event.parent_flow_run_id,
        notified=notified,
        payload=event.model_dump(mode="json"),
    )
    try:
        with session_factory() as session:
            session.add(record)
            session.commit()
    except SQLAlchemyError as error:
        logger.error("failed to persist (id={}): {}", failure_id, error)
        return False
    return True
```

> [!warning]
> A database outage must not turn a failure report into a `500` and a lost alert. Every path that touches storage or Slack either degrades gracefully or is caught — the only deliberate exception is a bad ingest token, which returns `401`.

## Why a shared bearer token, not something fancier

`/failures` sits behind a single shared token, checked with a plain `Authorization: Bearer` header. I could have reached for per-producer credentials, mTLS, or SigV4-signed requests instead. I didn't, because the threat model is narrow: every caller is a job I control, running in my own AWS account, and the only thing the token protects against is *someone else's* traffic hitting the ingestion path. A shared secret checked on every request is enough for that, and it's trivial for a Prefect flow or an ECS task to send. If de-hero ever accepts events from outside my own infrastructure, this is the first thing that would need to change — not before.

## Talking to Postgres

Storage is plain <FancyLink linkText="SQLAlchemy" url="https://www.sqlalchemy.org/" dark="true"/> against RDS Postgres — no async driver, no ORM cleverness, matching the rest of the service:

<FileName>
  de_hero/db.py
</FileName>
```python
def build_engine(database_url: str) -> Engine:
    return create_engine(database_url, pool_pre_ping=True)


def build_session_factory(engine: Engine) -> sessionmaker[Session]:
    return sessionmaker(bind=engine, expire_on_commit=False)
```

`main.py` builds one engine and one session factory at startup and hands the factory around as `app.state.session_factory` — every request opens its own short-lived session with it (`with session_factory() as session: ...`), rather than sharing one connection across requests. `pool_pre_ping` matters more than it looks: RDS will silently close idle connections, and without it the *first* request after a quiet period gets a confusing "connection already closed" error instead of a transparent reconnect.

There's one table, `failure_events`, and it stores each event as one row with the validated payload kept as JSON, plus a handful of columns broken out for the things actually queried on:

<FileName>
  de_hero/models.py
</FileName>
```python
class FailureEventRecord(Base):
    __tablename__ = "failure_events"

    id: Mapped[UUID] = mapped_column(Uuid, primary_key=True)  # UUIDv7
    occurred_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), index=True)
    received_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
    job_name: Mapped[str] = mapped_column(String, index=True)
    app: Mapped[str] = mapped_column(String, index=True)
    parent_flow_run_id: Mapped[str | None] = mapped_column(
        String, nullable=True, index=True
    )
    notified: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    payload: Mapped[dict[str, Any]] = mapped_column(JSON)
```

The **UUIDv7** primary key is what makes `id` time-sortable, so ordering by id also orders rows chronologically without a second index. The rule for every other column is the same: it lives in `payload` by default, and only gets promoted to a real, indexed column once something actually needs to query or filter on it directly — `job_name` and `app` for the frontend's filters, `parent_flow_run_id` because the dedup lookup queries by it, `notified` because a later worker event reads it. Nothing is broken out speculatively.

## Migrating the schema with Alembic

That "promote a field when it's needed" rule means the schema changes often, in small steps, as features land — not once up front. That's the whole reason for <FancyLink linkText="Alembic" url="https://alembic.sqlalchemy.org/" dark="true"/>: each change is one reviewable, revertible migration file with an `upgrade`/`downgrade` pair, chained to the previous one by a revision id. This is a real migration from the project's history, promoting `job_name` out of the JSON payload once the frontend needed to filter on it:

<FileName>
  migrations/versions/..._add_job_name.py
</FileName>
```python
def upgrade() -> None:
    op.add_column(
        "failure_events",
        sa.Column("job_name", sa.String(), nullable=True),
    )
    op.execute("UPDATE failure_events SET job_name = payload->>'job_name'")
    op.alter_column("failure_events", "job_name", nullable=False)
    op.create_index(op.f("ix_failure_events_job_name"), "failure_events", ["job_name"])


def downgrade() -> None:
    op.drop_index(op.f("ix_failure_events_job_name"), "failure_events")
    op.drop_column("failure_events", "job_name")
```

The shape is always the same: add the column **nullable**, backfill it from data that already exists (here, straight out of the JSON payload with Postgres's `->>` operator), then tighten it to `NOT NULL`. Doing it in three steps instead of one migration that adds a `NOT NULL` column keeps existing rows from breaking the migration — there's no "add the column and hope nothing already in the table cares" step.

> [!tip]
> Alembic can autogenerate a migration by diffing the ORM models against the live schema (`alembic revision --autogenerate`), but for anything with a backfill step — like this one — the generated file is a starting point to edit, not the final migration. The model change and the data migration are two different concerns, and only one of them is mechanical.

This is the start of the **audit trail** from the vision post. Right now it just records what failed. Once Stage 2 adds human actions on top, this same store becomes the evidence base for deciding what's safe to automate.

## Where this leaves us

Stage 1 is intentionally boring where it matters: no AI, no queue, no fancy auth, just structured events, correct deduplication, clean Slack alerts, and a hard guarantee that failures reach a human. Every tool choice here optimizes for that guarantee over performance or generality — this is the foundation everything else sits on.

Next in the series: **teaching the model to read the failure**, where Bedrock turns a raw traceback into a short summary and a likely cause, with a deterministic fallback for when the AI call fails.
