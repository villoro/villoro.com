## Spark by default

{/*
The hook. Many teams reach for Spark the moment "pipeline" and "database" appear in the
same sentence. Very few teams actually have big tables. Paying for a cluster (startup,
config, ops) to move tables a small machine could move.
*/}

## Where the frontier really is

{/*
The three zones (fits in memory / a bit bigger than memory / really big). Teams that used
pandas on small tables think the next step is Spark. With DuckDB the "no Spark" frontier
is much higher than people think: out-of-core, spills to disk, one pass.
One concrete anchor: e.g. 300M rows / 202 tables on a 4 vCPU / 8 GB task.
*/}

## The trade-off: you write the write logic

{/*
The one real cost: awswrangler handled append / merge / overwrite / schema evolution for
us. With DuckDB on Glue Iceberg we wrote it ourselves, plus its limits (no DROP / CREATE
OR REPLACE, no commit retries, overwrite = DELETE + INSERT, compaction afterwards).
*/}

## What we learned

{/*
Only the lessons that generalise, kept short:
- The source database is the bottleneck: more concurrency / bigger machine did not help.
- Memory is a working set, not a total.
- Where one machine actually stops: the disk for spill.
*/}
