## How a failure gets resolved

{/* The data model + write path.
- ResolutionCategory enum: hero-owned fixed set (fixed_bug, retried, upstream_fixed,
  config_change, wont_fix, not_an_issue) + auto_resolved, the one machine-set value.
- Resolution is a nullable column: null = unresolved, no separate bool flag.
- update_resolution sets/clears it, exposed via PATCH /api/failures/{id}.
- The sibling cascade: resolving one of a Prefect-flow/ECS-task pair resolves both
  (same prefect_flow_id or parent_flow_run_id). Explained here once; auto-resolve reuses
  it. Maybe a ### subsection for the cascade. */}

## Auto-resolving on success

{/* POST /success -> auto_resolve_failures. Self-healing pipelines: a later successful
run supersedes an earlier failure (same job_name + app, failure occurred before the
success). Reuses update_resolution, so the same sibling cascade applies, and marks
auto_resolved. */}
